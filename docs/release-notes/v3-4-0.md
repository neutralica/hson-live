



# Overview

This release completes a major architectural convergence across HSON representations, LiveMap authority, LiveHost runtime boundaries, hosted execution, and deployment topology.

It closes several historical ambiguities around representation identity, hosted authority, package boundaries, and runtime ownership.

---

# Representation Integrity and Binary HSON

## Binary HSON is now a first-class canonical representation

Binary HSON is no longer only a serialization experiment. It is now a complete representation lane alongside HSON, JSON, and HTML.

Binary encoding preserves the full canonical graph model, including:

- node kinds;
- object ordering;
- array structure;
- element/content distinctions;
- metadata;
- identity metadata;
- empty/present distinctions;
- text segmentation;
- JavaScript numeric edge cases;
- exact string representation behavior.

The binary layer does not redefine identity.

It answers:

```text
canonical graph
    ↓
binary representation
    ↓
deterministic bytes
```

rather than:

```text
canonical graph
    ↓
alternate identity model
```

---

## Representation hashing is representation-scoped

SHA-256 support now belongs to representation boundaries.

The system distinguishes:

```text
graph equality
representation equality
byte equality
```

A hash describes the emitted representation itself.

Textual representations use:

```text
serialized output
    ↓
UTF-8 bytes
    ↓
SHA-256
```

Binary uses:

```text
encoded Uint8Array
    ↓
SHA-256
```

No normalization or graph-level canonicalization is introduced by hashing.

Equivalent information expressed through different representations may intentionally produce different hashes.

# LiveMap, Locus, and Runtime Authority

## LiveMap remains canonical state authority

The runtime continues to separate:

```text
state
meaning
execution
```

LiveMap owns canonical graph state.

It does not own:

- application workflows;
- transport concerns;
- external authorization;
- runtime lifecycle.

---

## Locus is the authority boundary around LiveMap

Locus now represents the authoritative operational context around a LiveMap.

It owns:

- ordered mutation admission;
- revision history;
- synchronization;
- recovery;
- sessions;
- action lifecycle;
- subscriptions;
- authority transitions.

Application code requests meaning.

Locus enforces authority.

LiveMap stores resulting state.

---

## Application and runtime responsibilities remain separated

The architecture now consistently distinguishes:

```text
Application:
    what should this action mean?

Locus:
    is this mutation authoritative?

LiveMap:
    what state results?

LiveHost:
    how does this application run?
```

This prevents application semantics, state authority, and infrastructure lifecycle from collapsing into one layer.

---

# LiveHost and Hosted Runtime

## Node LiveHost is the complete runtime authority

The Node runtime now provides the complete execution environment for hosted applications.

It owns:

- HTTP ingress;
- WebSocket transport;
- application registration;
- runtime lifecycle;
- process boundaries;
- security policy;
- shutdown behavior;
- service-level health.

Node LiveHost is not a replacement for Locus.

It is the environment in which Locus-backed applications operate.

---

## Worker is now a compatibility runtime

The Worker architecture remains supported, but its role is clearer.

Worker provides:

- platform compatibility;
- portable execution;
- adapter validation.

It is not the complete runtime authority.

The distinction is:

```text
Node:
    full application runtime

Worker:
    constrained compatibility runtime
```

The shared application model remains intact while runtime capabilities differ.

---

# Hosted Execution and Runtime Boundaries

## Hosted execution now has explicit environmental authority

Execution no longer depends on ambient developer state.

The runtime boundary now defines:

- source state;
- dependency state;
- environment state;
- process ownership;
- artifact state.

The system distinguishes:

```text
what code exists
from
what environment happens to be installed
```

This closes a class of hidden workstation dependencies.

---

## Dependency ownership is explicit

Runtime dependencies now follow owned execution boundaries.

The model is:

```text
prepared dependency state
    ↓
runtime-owned dependency state
    ↓
execution
```

Rather than:

```text
execution
    ↓
whatever dependencies exist locally
```

This allows repeatable execution without making developer machines part of the runtime.

---

# Artifact and Build Integrity

## Build outputs are validated through relationships, not appearance

Artifact validation moved away from filename assumptions.

A file that looks generated is not necessarily generated.

The system now reasons from artifact relationships:

```text
emitted root
    ↓
references
    ↓
required outputs
```

rather than:

```text
filename pattern
    ↓
assumed provenance
```

This applies especially to generated frontend assets, where output naming alone does not establish ownership.

---

## Package boundaries reflect architectural boundaries

The public package surface now intentionally exposes subsystem boundaries.

Public imports represent supported architecture:

```text
hson-live
hson-live/locus
hson-live/locus/node
```

rather than incidental filesystem layout.

Generated package artifacts, declarations, and runtime exports are treated as one coherent public surface.

---

# Identity and Continuity

## QUID remains continuity metadata, not traversal authority

The identity model continues to distinguish:

```text
Path:
    what exists here now?

QUID:
    where did this subject continue from?
```

QUIDs support continuity across movement.

They do not replace canonical addressing.

Path remains mutation authority.

---

# Deployment Topology

## Deployment state is now part of runtime correctness

The deployment architecture now recognizes that runtime correctness depends on coherent repository state.

The deployment workspace is treated as a composed runtime:

```text
hson-demo2
    +
hson-live
    +
deployment configuration
```

A stale sibling runtime dependency is therefore a deployment correctness issue, not an application compatibility issue.

---

## Deployment authority is converging on Node runtime

The runtime architecture already exists.

The remaining transition is deployment wiring:

```text
static application
    ↓
Node hosted endpoint
    ↓
Node LiveHost
    ↓
Application
    ↓
Locus
    ↓
LiveMap
```

No new runtime layer is required.

No changes were required to:

- Generic LiveHost API;
- Node LiveHost API;
- Locus API;
- canonical HSON model;
- public representation APIs.
