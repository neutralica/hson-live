// v3-4-0.md | release notes

# Changes:



Assuming this chat corresponds to the post-v3.3 work, I’d summarize the release-level changes this way:

- **Renamed the one-LiveMap authority subsystem from LiveHost to Locus and hard-cut the public API accordingly.** Added `hson-live/locus` and `hson-live/locus/node`; renamed the one-map surface to `Locus*`, including `create_locus`, `create_locus_client`, `create_persistent_locus`, `LocusClientId`, `LocusLogicalMapId`, `LocusIncarnationId`, and `LocusSelector`. Removed the old one-map `hson-live/livehost` surface, compatibility aliases, forwarding shims, `hello.hostId`, `?livehost=`, `authoritySelector`, versioned bootstrap forms, and one-map `LIVEHOST_*` / `"livehost"` error and trace branding.

- **Flattened and clarified LiveMap/Locus representations, recovery, persistence, and bootstrap contracts.** Removed legacy/exact/versioned capture families, `formatVersion`/`viewStateVersions` generation machinery, legacy QUID-only canonical commit compatibility, and redundant protocol decoders. The current bootstrap is now the unversioned `LocusBootstrap` with format `"hson-locus-bootstrap"`, media type `application/vnd.hson-live.locus-bootstrap+hson`, and `locusSelector`; canonical history and persistence remain path-authoritative while raw-QUID request targeting continues to lower to paths.

- **Established the new generic LiveHost application-runtime boundary above Locus.** Added `hson-live/livehost` with platform-neutral `LiveHost`, `LiveHostApplication`, Web `Request`/`Response` routes, `LiveHostConnection` (`string | Uint8Array`), `LiveHostPrincipal`, lifecycle/readiness contracts, and `create_livehost_locus_registry`. The existing `hson-live/livehost/node` runtime was adapted to this model, making zero-Locus applications first-class while keeping application topology and Locus selection application-owned. The bounded registry gained `automaticSweep?: boolean` so applications can explicitly own idle scheduling when required.

- **Migrated and certified the first-party demo/runtime stack against the new architecture.** `hson-demo2` was moved from the old one-map LiveHost API to Locus plus generic LiveHost, including TOWL, hosted Test, circuit verification, Node hosting, store/disposal flows, routing, bootstrap, protocol fixtures, and lifecycle handling. Along the way, Node `Response` transport was corrected to stream with backpressure and repeated-header support, registry capacity was made safe under concurrent acquisitions, deterministic idle-sweep behavior was restored, and final U12 certification closed the LiveMap/Locus/LiveHost architecture with no unresolved production or public-surface defects.

# Representation Integrity and Binary Hson

## HsonBinary - a first-class canonical representation

Implemented Binary Hson as an output constructor option.

Binary encoding preserves the full canonical graph model for deterministic compressed representation.

---

## Hson hashing

Implemented SHA-256 support as an output constructor option. A hash describes the emitted serialization after canonicalization. Any format (JSON, Hson, or HTML) can be output as a SHA-256 hash for portable diagnostics.

---

# LiveMap, Locus, and Runtime Authority

## LiveMap remains canonical state authority

The runtime continues to separate:

```text
state
meaning
execution
```

LiveMap owns canonical graph state.

It does not own:

- application workflows;
- transport concerns;
- external authorization;
- runtime lifecycle.

---

## Locus is the authority boundary around LiveMap

Locus now represents the authoritative operational context around a LiveMap.

It owns:

- ordered mutation admission;
- revision history;
- synchronization;
- recovery;
- sessions;
- action lifecycle;
- subscriptions;
- authority transitions.

Application code requests meaning.

Locus enforces authority.

LiveMap stores resulting state.

---

# LiveHost and Hosted Runtime

## LiveHost is the complete runtime authority

The LiveHost runtime now provides the complete execution environment for hosted applications.

It owns:

- HTTP ingress;
- WebSocket transport;
- application registration;
- runtime lifecycle;
- process boundaries;
- security policy;
- shutdown behavior;
- service-level health.

LiveHost and Locus are now separate systems: LiveHost is the environment in which Locus-backed applications operate.

---

## Worker is now a compatibility runtime

The Worker architecture remains supported, but its role is clearer as a compatibility intermediary.

Worker provides:

- platform compatibility;
- portable execution;
- adapter validation.

The shared application model remains intact while runtime capabilities differ.

---

# Hosted Execution and Runtime Boundaries

## Hosted execution now has explicit environmental authority

Execution no longer depends on ambient developer state.

The runtime boundary now defines:

- source state;
- dependency state;
- environment state;
- process ownership;
- artifact state.

The system distinguishes:

```text
what code exists
from
what environment happens to be installed
```

This closes a class of hidden workstation dependencies.

---

## Dependency ownership is explicit

Runtime dependencies now follow owned execution boundaries.

The model is:

```text
prepared dependency state
    ↓
runtime-owned dependency state
    ↓
execution
```

Rather than:

```text
execution
    ↓
whatever dependencies exist locally
```

This allows repeatable execution without making developer machines part of the runtime.

---

# Artifact and Build Integrity

## Build outputs are validated through relationships, not appearance

Artifact validation moved away from filename assumptions.

A file that looks generated is not necessarily generated.

The system now reasons from artifact relationships:

```text
emitted root
    ↓
references
    ↓
required outputs
```

rather than:

```text
filename pattern
    ↓
assumed provenance
```

This applies especially to generated frontend assets, where output naming alone does not establish ownership.

---

## Package boundaries reflect architectural boundaries

The public package surface now intentionally exposes subsystem boundaries.

Public imports represent supported architecture:

```text
hson-live
hson-live/locus
hson-live/locus/node
```

rather than incidental filesystem layout.

Generated package artifacts, declarations, and runtime exports are treated as one coherent public surface.

---

# Identity and Continuity

## QUID remains continuity metadata, not traversal authority

The identity model continues to distinguish:

```text
Path:
    what exists here now?

QUID:
    where did this subject continue from?
```

QUIDs support continuity across movement.

They do not replace canonical addressing.

Path remains mutation authority.

# Deployment Topology

## Deployment state is now part of runtime correctness

The deployment architecture now recognizes that runtime correctness depends on coherent repository state.

The deployment workspace is treated as a composed runtime:

```text
hson-demo2
    +
hson-live
    +
deployment configuration
```

A stale sibling runtime dependency is therefore a deployment correctness issue, not an application compatibility issue.

---

## Deployment authority is converging on Node runtime

The runtime architecture already exists.

The remaining transition is deployment wiring:

```text
static application
    ↓
Node hosted endpoint
    ↓
Node LiveHost
    ↓
Application
    ↓
Locus
    ↓
LiveMap
```

No new runtime layer is required.

No changes were required to:

- Generic LiveHost API;
- Node LiveHost API;
- Locus API;
- canonical Hson model;
- public representation APIs.

### Binary Hson was finalized as a first-class representation surface

- Added the public Binary Transform surface:
  - `toBinary()`
  - `fromBinary()`
  - `TransformBinarySerialize.serialize(): Uint8Array`
  - Binary `.sha256(): Promise<string>`
- Chose `toBinary()` / `fromBinary()` over lower-level `encode` / `decode` naming for the public Transform API.
- Kept Binary output runtime-neutral as `Uint8Array`; no Node `Buffer` surface was added.
- Settled a deterministic binary grammar with:
  - `Hson` marker;
  - explicit type discriminators;
  - fixed big-endian counts;
  - finite numbers as IEEE-754 `f64be`;
  - deterministic record ordering;
  - strict encode/decode closure.
- Binary strings encode JavaScript UTF-16 code units so lone surrogates remain representable exactly.
- QUIDs remain ordinary canonical metadata strings rather than gaining a Binary-specific identity encoding.
- Added explicit decode limits for bytes, graph depth, and graph node count.
- Deliberately did **not** introduce a format/protocol version field yet.

---

### Binary implementation hardened canonical-graph admission rules

- Canonicality now includes JavaScript property-storage semantics, not just equivalent lookup values.
- Typed-style fields must be enumerable own data properties; inherited, accessor-backed, and non-enumerable semantic fields reject.
- Typed-style `unit` preserves three distinct states:
  - absent;
  - own-present `undefined`;
  - own-present string.
- Applied the same own-property discipline to `$_attrs` and `$_meta`.
- Preserved the distinction between absent metadata and present empty `$_meta`.
- Kept empty `$_attrs` noncanonical.
- Hardened Hson node storage:
  - `$_tag` and `$_content` must be own enumerable data properties;
  - `$_content` must be dense;
  - inherited/accessor-backed structural fields reject.
- Removed an accessor-related hazard in array-order normalization.

---

### Representation SHA-256 became part of the public representation model

- Added `.sha256()` to supported textual Transform terminals and Binary serialization.
- Defined hashes as **representation hashes**, not graph hashes.
- Textual SHA is computed from exact serializer output encoded with `TextEncoder`.
- Binary SHA is computed directly from emitted `Uint8Array` bytes.
- WebCrypto remains the portable implementation boundary.
- No serializer repair or normalization is performed to stabilize hashes.

---

### Representation integrity remained subordinate to canonical equality

- SHA witnesses supplement rather than replace:
  - canonical graph equality;
  - exact representation equality.
- Kept representation/circuit SHA logic inside `hson-live` diagnostics rather than promoting it into higher application layers.

---

### Application meaning remained outside Locus and LiveHost

- Hosted runtime expansion did not move application-specific concepts into generic library layers.
- Application still owns meanings such as:
  - catalog composition;
  - run/cancellation semantics;
  - coordinator/report topology;
  - executor selection.
- Locus continues to own authority mechanics around a single LiveMap.
- LiveHost continues to own runtime/transport infrastructure rather than application vocabulary.

---

### Process/runtime ownership was hardened without expanding the public library API

- Internal Node process supervision now treats process-group settlement, not direct child exit, as authoritative completion.
- Added TERM → bounded grace → KILL fallback semantics for resistant descendants.
- Browser and opaque-process execution use the same owned-process lifecycle.
- No generic public process-management API was added to LiveHost.

---

### Public Locus package boundaries were reinforced

- Confirmed the intended public package subpaths:
  - `hson-live/locus`
  - `hson-live/locus/node`
- Their build targets remain under the intentional API output layout (`dist/api/locus/...`) rather than exposing incidental source paths.
- When deployment consumed an older library revision lacking those exports, the consumer revision was advanced rather than adding fallback aliases or alternate import paths.

---

### Node production composition was made explicit

- Consolidated the existing Node runtime as the complete hosted application boundary rather than introducing another generic runtime layer.
- The production composition already provides:
  - HTTP/WebSocket ingress;
  - application registration;
  - origin/authentication policy;
  - health reporting;
  - graceful shutdown.
- Added/clarified production build and start boundaries around the existing Node artifact rather than changing LiveHost or Locus APIs.
- Kept Worker support as a constrained compatibility runtime rather than growing the library around Worker limitations.

---

### Authentication and runtime configuration remain outside browser/public API expansion

- Kept bearer credentials server-side.
- Did not add browser token APIs, login APIs, or public credential-management surfaces.
- Browser production authentication remains an external cookie/proxy concern.
- Runtime configuration remains environment-driven (`LOCUS_*`) rather than becoming new library API.

---

### Node became the complete runtime target without library API churn

- Confirmed that the existing Node stack already supports the full application/runtime capability set needed by hosted applications.
- Worker and Node continue to share application semantics, while Node owns capabilities unavailable in Worker such as processes, filesystem work, build tools, and Chromium.
- No new protocol, LiveHost abstraction, Locus abstraction, or compatibility shim was required.

---

## Transform — authored Hson provenance and canonical admission
- Extended the canonical authored-Hson path around hson.transform.string(...) / hsonString(...) so accepted authored source retains enough provenance for later diagnostics and source mapping rather than becoming immediately source-anonymous.
- Kept authored strings flowing through the same strict canonical admission boundary: parse → canonical graph → detached public value, rather than introducing a parallel provenance-aware parser.
- Preserved the existing Transform family (hson.transform.string, .number, .calc, with hsonString, hsonNumber, hsonCalc aliases); the substantive change here was to the authored-string/canonical boundary rather than adding another transformation namespace.
- Provenance remains descriptive evidence about the admitted source; it does not weaken canonical equality or make source spelling part of graph semantics.
- Added/hardened boundary diagnostics so provenance survives far enough to map failures back to the authored input while canonical Hson remains the semantic authority.

## Schema — small alignment with the current Document/LiveMap model
- No significant new public Schema surface landed in this tranche.
- Tightened internal Schema/Document interaction so schema enforcement follows the same document-location/path semantics as ordinary LiveMap document operations rather than maintaining special parallel interpretations.
- Continued convergence around reusable schema definitions and the existing tag/catalog machinery; this was principally consistency work rather than a new Schema feature set.
- In changelog terms I’d characterize this as Schema enforcement/path alignment and internal cleanup, not a Schema redesign.

## LiveHost — production capability validated without expanding the library API
- Confirmed that the existing hson-live/livehost/node surface already supports arbitrary application composition, HTTP routes, WebSocket upgrades, exact path routing, query preservation, security/authorization hooks, limits/backpressure, readiness, and graceful shutdown.
- The new public TOWL + Circuit runtime was composed entirely above that existing surface; no new hson-live public API or LiveHost-specific framework layer was required.
- This is worth noting because it materially validates LiveHost’s intended application-host role: a real public runtime can be assembled without Express or another application framework.
- Most production changes therefore remained demo/deployment composition rather than library code.

## Internal diagnostics/test-launcher contract — inventory authority simplified
- Removed executableChecks and the generic requirement that a launcher’s observed check count match a separately predicted count.
- Opaque launcher cardinality is now observed after execution (observedChecks) rather than declared as a permission gate; declaredChecks remains only where cardinality itself is genuinely semantic.
- Removed several related mutable-inventory gates and redundant totals where exact identity/hash reconciliation already proves completeness.
- Exact launcher identity, malformed/missing/duplicate results, failures, timeouts, cancellation, process errors, and other real protocol defects remain strict.
- This is internal infrastructure rather than public API, but it materially simplifies the library’s diagnostics contract: semantic identity is authoritative; current inventory totals are telemetry.

## Architectural conclusions and lessons from false starts

- **Binary should preserve JavaScript's actual canonical value space**, including UTF-16 edge cases, rather than forcing all values through ordinary Unicode-text assumptions.
- **Canonicality includes property ownership and descriptor semantics**, not just values returned by lookup.
- **Hashes belong to representations**, not abstract Hson graph identity.
- **Generated-output provenance should follow explicit relationships**, not filename appearance.
- **A process exiting does not imply the resources it owns are gone.**
- **Isolation should expose hidden dependencies rather than inherit ambient developer state until things happen to pass.**
- **When a consumer is stale, advance the consumer rather than weakening the public API.**
- **Do not add generic runtime abstractions simply because a new application capability exists.**
- **Node and Worker can share application semantics without pretending they provide equivalent runtime capabilities.**
- **Deployment coherence is an operational responsibility, not something the library should compensate for with permissive APIs.**

---

## Architectural work deliberately deferred

- **Ambient DOM/global audit**
  - classify LiveTree operations that depend on `window`, `document`, DOM constructors, layout APIs, observers, and other ambient browser state.
- **LiveTree SSR-readiness audit**
  - separate structural/runtime behavior from browser realization;
  - determine what works detached or with no DOM.
- **LiveTree runtime-resource ownership**
  - listeners;
  - CSS;
  - keyframes;
  - animations;
  - canvas;
  - timers/observers;
  - teardown, detach/reinsert, replacement, and remount behavior.
- **Reflection / LiveTree / LiveMap boundary audit**
  - especially authority assumptions and browser-dependent realization.
- **CSS/runtime-resource audit** as a dedicated follow-on.
- **Deterministic-operator archaeology** before settling SSR architecture.
- **SSR architecture itself**, intentionally deferred until the ownership audits are complete.
- **Longer-range Hson work**
  - schema integration;
  - stronger branded values;
  - richer arithmetic/transform facilities;
  - random generation;
  - broader diagnostic/error redesign.

**Binary and representation integrity expanded the public representation surface, while extensive runtime growth validated the existing LiveMap → Locus → Application → LiveHost separation without requiring the generic library architecture to grow around every new capability.**
